# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Unity **6000.3.5f2** (Unity 6) student project for "Motores de Desarrollo I": a third-person action/survival prototype built on URP. Code comments, logs and commit messages are written in Spanish (Rioplatense); keep that convention. Team members work on personal branches (e.g. `PabloBasile`, `Gianluca`, `LautaroPeruchena`) and merge into `main` via GitHub PRs.

## Building / running

There is no CLI build, lint or test setup — everything runs through the Unity Editor. The `.csproj`/`.slnx` files are regenerated by Unity and are not the source of truth. Scripts compile only when Unity reimports them, so verify compile errors in the Unity Console. `com.unity.test-framework` is installed but no tests exist.

Build scenes (in order, `ProjectSettings/EditorBuildSettings.asset`): `Mission_Controls` → `Town` → `Dungeon`. `EnemyTest.unity` is a sandbox scene. `_Recovery/`, `TutorialInfo/`, `DoubleL/Demo` and `Starter Assets/Sample` are not part of the game.

## Architecture

All game code lives in `Assets/Scripts/` (compiled into the default `Assembly-CSharp`; only Starter Assets have their own asmdefs).

**The player actually in use is `Assets/Prefabs/Player.prefab`**, which combines Unity Starter Assets' `ThirdPersonController` + `StarterAssetsInputs` for movement with project scripts: `PlayerHealth` (file `HealthPlayer.cs`), `Combat1` (file `Combat.cs`), `PlayerInteraction`, `InventoryUI`, and the custom orbit `Camera` (class named `Camera`, which shadows `UnityEngine.Camera` in the global namespace — qualify it when you need the engine type).

There is also an older, more elaborate Souls-like player system that is **not referenced by any scene or prefab**: `PlayerController` (file `PlayerController1.cs`), `PlayerCombat` (combos, parry/block, weapon table), `PlayerStats` (stamina, poise, estus, souls, status effects, rally), `WeaponManager`, `BonfireGoal`, `LootableItem`. They still must compile, so changes to shared types (e.g. `IDamageable`, `WeaponHitbox`, `PlayerInputActions`) must keep them building. Note `Bonfire` heals `PlayerHealth`, while `BonfireGoal` uses `PlayerStats`.

Class names often don't match file names (see above; also `LootItem` is in `LootBase.cs`). Search by class name, not file name.

### Cross-cutting patterns

- **Interfaces** (`Scripts/Interfaces/`): `IDamageable.TakeDamage(float)` is how everything deals damage (player weapon → enemies, enemy hitbox → player). `IInteractable.Interact(GameObject interactor)` is triggered by `PlayerInteraction`, which raycasts forward from the player on `interactableLayer` and resolves the component with `GetComponentInParent`. Implementers: `Door`, `LootItem`, `ShopTrigger`, `LootableItem`.
- **Hitboxes**: `WeaponHitbox` is a trigger collider disabled by default, toggled on only during the attack window by the combat script, and it raises an `OnHit` event instead of applying damage itself. `EnemyHitbox` is the enemy counterpart (activated during `EnemyDasher`'s dash).
- **Input**: two approaches coexist. `PlayerInputActions.cs` is the generated C# class from `Scripts/PlayerInputActions.inputactions` (used by `Combat1`/`PlayerController` via `new PlayerInputActions()`) — regenerate it from the asset rather than hand-editing. Other scripts (`PlayerInteraction`, `InventoryUI`) query the project-wide actions via `InputSystem.actions.FindAction("Interact"/"Inventory")`, which come from `Assets/InputSystem_Actions.inputactions`. `WeaponManager` still uses the legacy `Input` class.
- **Cross-scene state is static**: `InventoryUI.inventory` (List<LootData>) and `InventoryUI.money` hold the player's items/money; `ShopManager.staticShopStock` holds the shop stock. `Door` checks keys by matching `LootData.ItemName` against `InventoryUI.inventory`. There is no DontDestroyOnLoad or save system.
- **Items** are `LootData` ScriptableObjects (created as assets, or at runtime via `LootData.Create`). Enemies drop a loot prefab containing `LootItem`, which adds its `LootData` to the interactor's `InventoryUI`.
- **Scene flow**: `SceneTeleportTown`/`SceneTeleportDungeon` triggers and `SceneLoader.LoadNextScene` load scenes by name; player death (`PlayerHealth.Die`) reloads `"Dungeon"`. Renaming a scene breaks these string references.
- Many components rely on the `"Player"` tag and on layer masks assigned in the Inspector (`hittableLayers`, `interactableLayer`, `obstacleMask`). Most tuning values are `[SerializeField]`, so prefab/scene overrides may differ from code defaults.

### Editing Unity assets

Don't edit `.unity`, `.prefab` or `.asset` YAML by hand unless necessary; wiring is normally done in the Inspector. Always keep `.meta` files alongside moved/renamed assets (GUIDs are how scenes/prefabs reference scripts).
