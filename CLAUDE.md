# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Unity **6000.3.5f2** (Unity 6) student project for "Motores de Desarrollo I": a third-person action/survival prototype built on URP. Code comments, logs and commit messages are written in Spanish (Rioplatense); keep that convention. Team members work on personal branches (e.g. `PabloBasile`, `Gianluca`, `LautaroPeruchena`) and merge into `main` via GitHub PRs.

## Building / running

There is no CLI build, lint or test setup — everything runs through the Unity Editor. The `.csproj`/`.slnx` files are regenerated by Unity and are not the source of truth. Scripts compile only when Unity reimports them, so verify compile errors in the Unity Console. A quick compile check without the Editor works with `dotnet build Assembly-CSharp.csproj` (uses the Unity-generated csproj; newly created scripts may be missing until Unity regenerates it). `com.unity.test-framework` is installed but no tests exist.

Build scenes (in order, `ProjectSettings/EditorBuildSettings.asset`): `MainMenu` → `Mission_Controls` → `Town` → `Dungeon`, plus `MainVictory`/`MainDefeat` (nothing loads them yet). `EnemyTest.unity` is a sandbox scene. `_Recovery/`, `TutorialInfo/`, `DoubleL/Demo` and `Starter Assets/Sample` are not part of the game.

## Architecture

All game code lives in `Assets/Scripts/` (compiled into the default `Assembly-CSharp`; only Starter Assets have their own asmdefs).

**The player actually in use is `Assets/Prefabs/PlayerKnight.prefab`** (Town and Dungeon), the Souls-like system. Its `Player` child has `PlayerController` (file `PlayerController1.cs`: movement with root motion, roll, lock-on, input through `PlayerInputActions.IPlayerActions`), `PlayerCombat` (combos, parry/block, weapons), `PlayerStats` (stamina, poise, estus, souls, rally), `PlayerWeaponSheath` (draw/sheathe), `PlayerInteraction` and `InventoryUI`. The `KnightModel` child has the Animator plus `PlayerRootMotion`, `PlayerFootsteps` and `PlayerLantern`; the camera is Cinemachine with `PlayerCameraRig`. The prefab and `Animations/Player/PlayerKnight.controller` are generated from scratch by the editor tool `Scripts/Editor/PlayerKnightSetup.cs` (Tools > Player > Armar Player Knight), so structural changes to either should also go into the tool. In Town, `ZoneSettings.LanternMode` turns combat off (lantern exploration). Town's night look comes from its Lighting settings (exp² fog 0.04, trilight ambient, skybox `Assets/Settings/TownNightSky.mat` = Skybox/Cubemap with the Poly Haven CC0 HDRI `rogland_clear_night_2k.hdr` (imported as a cube, `_Exposure` 0.8); Town's `NightAtmosphere.backgroundMatchesFog` is off so the sky shows), the "Luna" directional light (intensity 0.6) and `Assets/Settings/TownNightProfile.asset`; `Scripts/Editor/TownAtmosphereSetup.cs` sets the same values, so change both together. Dungeon walls/floors are Ariel's ProBuilder meshes with `Models/Dungeon/Materials/Cave wall.mat` (his Rock035 texture, parallax 0.08) and `Cave floor.mat` (Poly Haven CC0 `cobblestone_floor_01`, 2K diffuse + normal + height/parallax, tiling 0.5); the Floor2 hall roof uses his `Cave roof.mat` (Rock012, slight emission). All their textures are in `Models/Dungeon/Textures/`. Wall and floor have no emission on purpose (Ariel had added some; it brightens the dark Dungeon). `Scripts/Editor/DungeonWallsSetup.cs` (Tools > Dungeon > Paredes irregulares) subdivides the "Cave wall" ProBuilder meshes (`ConnectElements.Connect` until edges ≤ 1.5 m, max 4 passes) and offsets every vertex horizontally with world-space noise, so shared corners stay closed; processed meshes get " (irregular)" appended to their name and are skipped next time. The Dungeon's wall torches and bonfires are Ariel's: `Models/Dungeon/Decorations/Torch/Torch.fbx` instances, each with a `VFX_Fire_01_Small` and a Point Light (intensity 100, range 10), and `Decorations/Bonfire/bonfire_01.fbx` with floor fires. An alternative KayKit torch, `Assets/Prefabs/Torch.prefab` (origin = wall point, +Z out of the wall; not placed in any scene), is built by `Scripts/Editor/TorchPrefabBuilder.cs` ([InitializeOnLoad]: builds it once the model is imported; also Tools > Dungeon > Armar prefab de antorcha). It uses the CC0 model `Assets/Models/Torch/torch_mounted.fbx` (KayKit Dungeon Remastered by Kay Lousberg, with its `dungeon_texture.png` through `Torch KayKit.mat`), measured at build time (the horizontal axis it extends along from its origin = out of the wall) and scaled to 0.75 m high, plus the Vefects small fire (scale 0.7) sunk 8 cm into the head and a modest warm point light ("Luz", intensity 3, range 7, `FireFlicker`). The Vefects fire prefabs spawn strong white lights through a particle system named "Lights" (template `VFX_Point_Light.prefab`), not Light components, so the builder deactivates that child. The builder tags the prefab with an asset label (`BuildVersionLabel`); bump it when changing the builder so the prefab rebuilds itself once. The Dungeon is meant to be darker than Town: its own `Assets/Settings/DungeonNightProfile.asset` (post exposure -0.3), dark trilight ambient, exp² fog 0.045, background = fog color. `FogCulling` derives its cull distance from the fog density. Light reach was extended: the player's lantern (`LuzLampara`, range 15, `PlayerLantern.lightIntensity` 3; `LanternSetup` uses the same), Town's fire lights (range 20) and street lamp (16, intensity 3), the Dungeon fire (18) and the Vefects fire VFX light `VFX_Point_Light.prefab` (18), which all the fire VFX prefabs use.

The previous player, `Assets/Prefabs/Player.prefab` (Starter Assets `ThirdPersonController` + `StarterAssetsInputs`, `PlayerHealth` in `HealthPlayer.cs`, `Combat1` in `Combat.cs`, orbit camera `ThirdPersonCamera`), is **not used by any scene** but must still compile, as must `WeaponManager`, `BonfireGoal` and `LootableItem`. Changes to shared types (e.g. `IDamageable`, `WeaponHitbox`, `WeaponSO`, `PlayerInputActions`) must keep them building. Note `Bonfire` heals `PlayerHealth`, while `BonfireGoal` uses `PlayerStats`.

Class names often don't match file names (see above; also `LootItem` is in `LootBase.cs`). Search by class name, not file name.

### Weapon system (`Scripts/Weapons/`, used by `PlayerCombat` and `Combat1`)

- `WeaponTypeSO` (sword, axe...) holds the weight curves, lerped between `lightWeight` and `heavyWeight`: `GetSpeedMultiplier` (lighter → faster animation), `GetRecoveryTime` (lighter → shorter recovery) and `GetStaminaMultiplier` (lighter → cheaper hits). Its `attackClip` and `hitboxStart`/`hitboxEnd` are only used by `Combat1`; the knight keeps its own combo animations.
- `WeaponSO` extends `LootData` (name, description and price come from the item), so a weapon can be sold in the shop, dropped as loot and kept in `InventoryUI.inventory`. It adds type, `damage`, `weight` and an optional `modelPrefab`. Assets live in `Assets/Prefabs/Weapons/`: `Knight Sword` (the knight's default weapon, no model), `Basic Sword` (light) and `Heavy Sword` (heavy). Their prefabs are hand-written copies of the knight's own sword (mesh from `knight(b3_6).fbx`, root rotated 90° on X and scaled ×60.87 = the original sword's world scale, hitbox = mesh bounds) with tinted copies of `sword_mat` (`Basic Sword Mat` blue, `Heavy Sword Mat` dark red); the heavy one is scaled up (×1.4 width/thickness, ×1.15 length). The `Sword` type is `Scripts/Weapons/Sword.asset`.
- `PlayerCombat`: each hit deals `weapon.Damage × AttackData.damageMultiplier`, stamina cost is scaled by the weapon's stamina multiplier, and the speed goes to the float parameter `AttackSpeed` (speed multiplier of the four attack states in `PlayerKnight.controller`), with the hitbox timings divided by it. After an attack that doesn't chain, `RecoveryTime` blocks attacking again. Weapons are inventory items: the first time in a play session, `defaultWeapon` + `startingWeapons` (Knight, Basic and Heavy Sword) are added to `InventoryUI.inventory` and fill the equipped slots in order. There are `MaxEquipped` (2) equipped slots, static like the inventory so they survive scene loads; keys 1–2 choose which one is in the hand (`TakeInHand`). `EquipToSlot`/`Unequip` change the slots (at least one must stay equipped; not allowed mid-attack). `debugLogs` (on by default) logs every weapon change, attack (combo step, speed, stamina) and hit.
- Inventory (Tab): `InventoryUI` restyles the Canvas panel at runtime (dark background + gold `Outline`) and builds its single TMP text with rich text: a WEAPONS section and an ITEMS section where repeated items are grouped by `ItemName` ("x2"). Each weapon line has a TMP `<link>` (id = inventory index) for Equip/Unequip, detected in `Update` with `TMP_TextUtilities.FindIntersectingLink` on left click. While the inventory is open, `PlayerCombat.PerformAttack` does nothing so the click doesn't swing.
- Shop: `ShopManager.itemsForSale` (Inspector, on the shop in Town) adds asset items such as weapons to the stock. The buy list hides weapons already in the inventory and the sell list hides equipped ones. A bought weapon is equipped only if a slot is free.
- Models: `PlayerWeaponSheath` wraps the knight's sword in a runtime `WeaponHolder` (world scale 1, +Y toward the tip) and moves that between `SwordGrip` (hand) and `SwordHipSocket` (hip). `SetWeaponModel` instantiates the weapon's `modelPrefab` inside it with the prefab's own local transform and hides the original sword. Weapon prefabs are authored at real size with the grip at the origin, the blade along +Y and the guard along X. If a model has no `WeaponHitbox`, `PlayerCombat` adds a trigger BoxCollider sized to its meshes, and it disables the model's other colliders.
- `Combat1` (old `Player.prefab`) swaps `baseAttackClip` (`Enemy_Attack_1`) for the type's `attackClip` through a runtime `AnimatorOverrideController`, uses `AttackSpeed` on the attack state of `StarterAssetsThirdPerson.controller`, and instantiates models under `WeaponAttach`. `Basic Sword.prefab`'s root transform is now set up for the knight, not for that socket.
- **Starter Assets are locally modified**: `ThirdPersonController` has a public `CanMove` flag (used by `Combat1` to lock movement/rotation/jump), and the Starter controller has the `AttackSpeed` parameter. Keep these when updating/reimporting Starter Assets.
- Hit detection (`PlayerCombat`): during each attack's window (`swingWindowStart`–`swingWindowEnd`, normalized, so it scales with weapon speed), `FixedUpdate` sweeps the hitbox's BoxCollider with `Physics.OverlapBoxNonAlloc` (4 sub-steps between physics steps) and only counts hits while the blade center moves at least `minBladeSpeed` m/s. The `WeaponHitbox` trigger is only used for non-box hitboxes. Hits are deduplicated per swing by `IDamageable` (found with `GetComponentInParent`) and never hit the player's own hierarchy. `debugLogs` prints each swing's peak blade speed to tune `minBladeSpeed`.
- Enemies ignore hits within `EnemyDasher.damageCooldown` (0.3 s; it was 1.5 s and ate combo hits). `Combat1` doesn't deduplicate per swing.
- Combo: pressing attack while an attack is playing calls `PlayerCombat.QueueNextCombo` directly (not through `PlayerController`'s input buffer, which only runs once the state is back to Idle — too late to chain), and the next hit starts when the current one ends. A heavy attack ends the combo. `comboResetTime` counts from the end of the last hit.

### Cross-cutting patterns

- **Interfaces** (`Scripts/Interfaces/`): `IDamageable.TakeDamage(float)` is how everything deals damage (player weapon → enemies, enemy hitbox → player). `IInteractable.Interact(GameObject interactor)` is triggered by `PlayerInteraction`, which raycasts forward from the player on `interactableLayer` and resolves the component with `GetComponentInParent`. Implementers: `Door`, `LootItem`, `ShopTrigger`, `LootableItem`.
- **Hitboxes**: `WeaponHitbox` is a trigger collider disabled by default, toggled on only during the attack window by the combat script, and it raises an `OnHit` event instead of applying damage itself. `EnemyHitbox` is the enemy counterpart (activated during `EnemyDasher`'s dash). `EnemyDasher` also has a cyclic area attack (`secondAttack*` fields, started in `OnEnable`): every 20 s, once the player is within `detectionRange` and no dash is running, it shakes `visualTransform` for 1.5 s and then deals 30 damage within 5 m through `Physics.OverlapSphere`, filtered by the "Player" tag.
- **Audio**: Unity audio and FMOD coexist. Unity audio stays enabled (`ProjectSettings/AudioManager.asset` `m_DisableAudio: 0`; Ariel's FMOD setup had turned it off): `PlayerFootsteps` (`AudioSource.PlayClipAtPoint`) and the Vefects fire prefabs' AudioSources use it. FMOD for Unity lives in `Assets/Plugins/FMOD` (~300 MB, its own `FMODUnity`/`FMODUnityEditor` asmdefs). Town's ambience is FMOD: `StudioEventEmitter`s on `Burning_House_SFX`, `Burning_Windmill_SFX`, `Well_Drip_SFX`, `Wind_Bells_SFX`, `Windmill_SFX` and the `Forest_Area`/`Town_Area` trigger zones, loaded by `Fmodbankload` (`StudioBankLoader`). The knight's MainCamera has both an `AudioListener` and FMOD's `StudioListener`; `PlayerKnightSetup` adds both (FMOD's through reflection, so the tool compiles without FMOD). The FMOD Studio project is not in the repo: `Plugins/FMOD/Resources/FMODStudioSettings.asset` points to `../../Crown-of-Heresy/Crown-of-Heresy.fspro` and its `Build` folder on Ariel's machine, and `Assets/FMODBanks/*.bytes` are 16-byte "bank stub" placeholders. FMOD events only play where that project exists (elsewhere FMOD logs bank/event errors) until the project or its built banks are committed.
- **Input**: two approaches coexist. `PlayerInputActions.cs` is the generated C# class from `Scripts/Player/PlayerInputActions.inputactions` (used by `Combat1`/`PlayerController` via `new PlayerInputActions()`) — regenerate it from the asset rather than hand-editing. Some scripts read keys directly with `Keyboard.current` (`ShopTrigger`, weapon number keys in `PlayerCombat` and `Combat1`). Other scripts (`PlayerInteraction`, `InventoryUI`) query the project-wide actions via `InputSystem.actions.FindAction("Interact"/"Inventory")`, which come from `Assets/InputSystem_Actions.inputactions`. `WeaponManager` still uses the legacy `Input` class.
- **Health and stamina bars**: `PlayerStats` builds two `StatBarUI` at runtime: health in place of its `healthText` (the Canvas text, which moves inside the bar) and stamina right above it, fed by `OnStaminaChanged`. Health is burgundy, and its number uses `PlayerStats.barFont` (`Assets/fonts/BECKETT.asset`). The bars are sprite-less Images sized through `anchorMax.x`; a drop leaves a "chip" segment that waits `chipDelay` and then drains. `useHealthBar` off goes back to plain text. Stamina is spent by attacks (`PlayerCombat`, scaled by the weapon), rolls (`rollStaminaCost`), sprinting (`SprintStaminaCostPerSecond`) and blocked hits (`TryDefend`). At 0 stamina, sprinting stops until stamina is back to `PlayerController.sprintRecoverStamina` (25). The stamina bar is blue.
- **Cross-scene state is static**: `InventoryUI.inventory` (List<LootData>) and `InventoryUI.money` hold the player's items/money; `ShopManager.staticShopStock` holds the shop stock. `Door` checks keys by matching `LootData.ItemName` against `InventoryUI.inventory`. There is no DontDestroyOnLoad or save system.
- **Items** are `LootData` ScriptableObjects (created as assets, or at runtime via `LootData.Create`). Enemies drop a loot prefab containing `LootItem`, which adds its `LootData` to the interactor's `InventoryUI`.
- **Scene flow**: `SceneTeleportTown`/`SceneTeleportDungeon` triggers and `SceneLoader.LoadNextScene` load scenes by name; player death reloads `"Dungeon"` (`PlayerController.deathSceneName` on the knight, `PlayerHealth.Die` on the old player). Renaming a scene breaks these string references.
- Many components rely on the `"Player"` tag and on layer masks assigned in the Inspector (`hittableLayers`, `interactableLayer`, `obstacleMask`). Most tuning values are `[SerializeField]`, so prefab/scene overrides may differ from code defaults.

### Editing Unity assets

Don't edit `.unity`, `.prefab` or `.asset` YAML by hand unless necessary; wiring is normally done in the Inspector. Always keep `.meta` files alongside moved/renamed assets (GUIDs are how scenes/prefabs reference scripts).
