# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Unity **6000.3.5f2** (Unity 6) student project for "Motores de Desarrollo I": a third-person action/survival prototype built on URP. Code comments, logs and commit messages are written in Spanish (Rioplatense); keep that convention. Team members work on personal branches (e.g. `PabloBasile`, `Gianluca`, `LautaroPeruchena`) and merge into `main` via GitHub PRs.

## Building / running

There is no CLI build, lint or test setup — everything runs through the Unity Editor. The `.csproj`/`.slnx` files are regenerated by Unity and are not the source of truth. Scripts compile only when Unity reimports them, so verify compile errors in the Unity Console. A quick compile check without the Editor works with `dotnet build Assembly-CSharp.csproj` (uses the Unity-generated csproj; newly created scripts may be missing until Unity regenerates it). `com.unity.test-framework` is installed but no tests exist.

Build scenes (in order, `ProjectSettings/EditorBuildSettings.asset`): `MainMenu` → `Mission_Controls` → `Town` → `Dungeon`, plus `MainVictory` (loaded when the final boss dies) and `MainDefeat` (loaded when the player dies; its Try Again loads the save). `EnemyTest.unity` is a sandbox scene. `_Recovery/`, `TutorialInfo/`, `DoubleL/Demo` and `Starter Assets/Sample` are not part of the game (`DoubleL/FBX Unity` is: the enemy's animations use it).

### Weapon system (`Scripts/Weapons/`, used by `PlayerCombat` and `Combat1`)

- `WeaponTypeSO` (sword, axe...) holds the weight curves, lerped between `lightWeight` and `heavyWeight`: `GetSpeedMultiplier` (lighter → faster animation), `GetRecoveryTime` (lighter → shorter recovery) and `GetStaminaMultiplier` (lighter → cheaper hits). Its `attackClip` and `hitboxStart`/`hitboxEnd` are only used by `Combat1`; the knight keeps its own combo animations. The curves are clamped to the weight range, so the exaggerated weapons have their own types instead of extreme weights:
  - `Sword.asset`: weights 1–10, speed ×1.5–0.6, stamina ×0.4–2.2. These are explicit in the asset; the code defaults are 0.6–1.6, and the Heavy Sword cost only 1.7× the Basic.
  - `Rapier.asset`: weights 0.3–1.5, speed ×2.8–2.2, recovery 0–0.05 s, stamina ×0.08–0.2.
  - `Greatsword.asset`: weights 20–30, speed ×0.42–0.3, recovery 1–1.4 s, stamina ×4.2–5.2.
- `WeaponSO` extends `LootData` (name, description and price come from the item), so a weapon can be sold in the shop, dropped as loot and kept in `InventoryUI.inventory`. It adds type, `damage`, `weight` and an optional `modelPrefab`. Assets live in `Assets/Prefabs/Weapons/`:
  - `Knight Sword`: the knight's default weapon, no model.
  - `Basic Sword`: light.
  - `Heavy Sword`: heavy, damage 25.
  - `Featherlight Rapier`: Rapier type, damage 5, weight 0.5, about 2.7× speed, about 1 stamina per hit, thin gold model.
  - `Colossal Greatsword`: Greatsword type, damage 120, weight 25, about 0.36× speed, about 56 stamina for the first light hit, 1.2 s recovery, huge black model. Their prefabs are hand-written copies of the knight's own sword. The mesh comes from `knight(b3_6).fbx`, the root is rotated 90° on X and scaled ×60.87 (the original sword's world scale), and the hitbox is the mesh bounds, so it scales with the model. Each uses a tinted copy of `sword_mat`:

  | Prefab | Material | Width/thickness | Length |
  |---|---|---|---|
  | Basic | blue | ×1 | ×1 |
  | Heavy | dark red | ×1.4 | ×1.15 |
  | Rapier | gold | ×0.55 | ×1.15 |
  | Greatsword | near-black | ×2.4 | ×2.2 | The `Sword` type is `Scripts/Weapons/Sword.asset`.
- `PlayerCombat`: each hit deals `weapon.Damage × AttackData.damageMultiplier`, stamina cost is scaled by the weapon's stamina multiplier, and the speed goes to the float parameter `AttackSpeed` (speed multiplier of the four attack states in `PlayerKnight.controller`), with the hitbox timings divided by it. After an attack that doesn't chain, `RecoveryTime` blocks attacking again. Weapons are inventory items: the first time in a play session, `defaultWeapon` + `startingWeapons` are added to `InventoryUI.inventory` and fill the equipped slots in order. The player starts with only the Knight Sword: `startingWeapons` and `PlayerKnightSetup.StartingWeaponPaths` are empty, and the other weapons are bought in the shop. An attack's stamina cost is capped at the max stamina, so the Greatsword's heavy attack (×4.7 → about 140) can still be done with a full bar. There are `MaxEquipped` (2) equipped slots, static like the inventory so they survive scene loads; keys 1–2 choose which one is in the hand (`TakeInHand`). `EquipToSlot`/`Unequip` change the slots (at least one must stay equipped; not allowed mid-attack). `debugLogs` (on by default) logs every weapon change, attack (combo step, speed, stamina) and hit.
- Inventory (Tab): `InventoryUI` restyles the Canvas panel at runtime (dark background + gold `Outline`) and builds its single TMP text with rich text: a WEAPONS section and an ITEMS section where repeated items are grouped by `ItemName` ("x2"). Each weapon line has a TMP `<link>` (id = inventory index) for Equip/Unequip, detected in `Update` with `TMP_TextUtilities.FindIntersectingLink` on left click. While the inventory is open, `PlayerCombat.PerformAttack` does nothing so the click doesn't swing. Opening it moves its panel to the last sibling, so it draws above the shop, which is in the same Canvas.
  - The panel and `ItemListText` live in `Assets/Prefabs/Canvas.prefab`.
  - With many items the text ran out of the panel. At start, `SetupScrolling` wraps the text in a clipped "Lista" viewport: the text's old area, kept 24 px inside the panel, with a `RectMask2D` and a `ScrollRect`.
  - The text grows with a `ContentSizeFitter`. A thin gold scrollbar on the right appears only when needed.
  - `Update` reads the mouse wheel itself, so scrolling doesn't depend on an EventSystem. The list opens at the top, and link clicks outside the viewport are ignored.
  
  In the Editor, F9 with the inventory open gives every `LootData` asset in the project: missing weapons once each, and one more of every other item (key, Magic Cube). It finds them with `AssetDatabase`, under `#if UNITY_EDITOR`. `InventoryUI.OpenNow` is static, so the shop's F9 can skip while the inventory is on top.

- **Knight locomotion and footsteps**:
  - The `Locomotion` blend tree mixes "Unarmed" and "Armed" by the `Armed` parameter (`SetFloat` damped 0.15 s).
    - Unarmed is driven by `Speed`: Mixamo "Scared Idle", Mixamo "Cautious Walk", and Starter Assets `Run_N`, which is in place (XZ baked into pose).
    - Armed is DoubleL's 1Hand_Up 8-direction set, driven by MoveX/MoveY; it has root motion.
  - `PlayerController.ApplyRootMotion` measures once per set (unarmed/armed × walk/run) whether the clips move by themselves; in-place sets move by code.
    - It only measures once the `Armed` blend has settled (and, unarmed, `Speed` has reached the gait). Sheathing while running, or the roll's `SheatheInstant`, used to measure the armed run as the unarmed one. The unarmed run was then marked as root motion, so the knight ran in place in the Dungeon until he drew the sword.
    - Safety net: a set marked as root motion whose animation moves less than 10 % of the requested speed for 0.5 s switches to code movement. `debugMovement` logs both decisions.
  - `PlayerFootsteps` detects footfalls from the humanoid foot bones (`detectFootfalls`): a step sounds when a foot comes back down near its lowest point after lifting, only while Moving/Sprinting and actually moving. Only the unarmed run had `OnFootstep` animation events, so walking and running with the sword were silent. The events are still received; they play only with `detectFootfalls` off. `OnLand` is unchanged.
- **Floating markers** (`Scripts/Ambiente/FloatingMarker.cs`): an inverted triangle with a dark border marks where something is, so it can be seen from afar. In Town there is a yellow one over the shop and a red one over the dungeon entrance ("Door", which has `SceneTeleportDungeon`).
  - Each is an "Indicador" child of that object, placed by `Scripts/Editor/TownMarkersSetup.cs` where none exists yet; move the "Indicador" object to move it.
  - It bobs slowly and turns toward the camera around the vertical axis. The triangle itself is an unsaved HideAndDontSave object, like `WindowLightShaft`'s.
  - It draws with `Assets/Shaders/IndicadorSinNiebla.shader` ("Crown/Indicador (sin niebla)"): unlit, without fog, ZTest Always, so it shows through the fog and behind houses. The shader is referenced from the component so builds include it.
  - Beyond `constantSizeFrom` (20 m) it keeps its on-screen size.
  - Beyond 85 % of the camera's far clip (Town's `FogCulling` cuts it to ~70 m), it is drawn closer along the same line and smaller, so it looks the same on screen.
- Models: `PlayerWeaponSheath` wraps the knight's sword in a runtime `WeaponHolder` (world scale 1, +Y toward the tip) and moves that between `SwordGrip` (hand) and `SwordHipSocket` (hip). `SetWeaponModel` instantiates the weapon's `modelPrefab` inside it with the prefab's own local transform and hides the original sword. Weapon prefabs are authored at real size with the grip at the origin, the blade along +Y and the guard along X. If a model has no `WeaponHitbox`, `PlayerCombat` adds a trigger BoxCollider sized to its meshes, and it disables the model's other colliders.
- `Combat1` (old `Player.prefab`) swaps `baseAttackClip` (`Enemy_Attack_1`) for the type's `attackClip` through a runtime `AnimatorOverrideController`, uses `AttackSpeed` on the attack state of `StarterAssetsThirdPerson.controller`, and instantiates models under `WeaponAttach`. `Basic Sword.prefab`'s root transform is now set up for the knight, not for that socket.
- **Starter Assets are locally modified**: `ThirdPersonController` has a public `CanMove` flag (used by `Combat1` to lock movement/rotation/jump), and the Starter controller has the `AttackSpeed` parameter. Keep these when updating/reimporting Starter Assets.
- Hit detection (`PlayerCombat`): during each attack's window (`swingWindowStart`–`swingWindowEnd`, normalized, so it scales with weapon speed), `FixedUpdate` sweeps the hitbox's BoxCollider with `Physics.OverlapBoxNonAlloc` and only counts hits while the blade center moves at least `minBladeSpeed` m/s.
  - The knight's Animator runs in Animate Physics, so each physics step shows a new pose.
  - Between two poses, the box is tested at intermediate poses: enough that the tip moves at most `SweepSpacing` (0.1 m) between tests, from 4 to 40 of them.
  - `ArcLerp` places those poses on the cut's arc, as a screw motion around the axis derived from the two poses, falling back to a straight line.
  - For the test, the box is at least 0.06 m thick per half-axis.
  - The Featherlight Rapier at ×2.7 turns tens of degrees per step at 50–77 m/s. The old straight 4-step interpolation cut inside the arc, and its third combo hit never connected. The `WeaponHitbox` trigger is only used for non-box hitboxes. Hits are deduplicated per swing by `IDamageable` (found with `GetComponentInParent`) and never hit the player's own hierarchy. `debugLogs` prints each swing's peak blade speed to tune `minBladeSpeed`.
- Enemies ignore hits within `EnemyDasher.damageCooldown` (0.15 s). It was 1.5 s, which ate combo hits, then 0.3 s, which ate the Rapier's hits about 0.22 s apart. `Combat1` doesn't deduplicate per swing.
- Combo: pressing attack while an attack is playing calls `PlayerCombat.QueueNextCombo` directly (not through `PlayerController`'s input buffer, which only runs once the state is back to Idle — too late to chain), and the next hit starts when the current one ends. A heavy attack ends the combo. `comboResetTime` counts from the end of the last hit.
- Roll cancels an attack. Pressing roll mid-attack calls `PlayerCombat.CancelAttack` and rolls at once if `PlayerController.CanRoll` (grounded, enough stamina). The cancel stops the tracked `attackRoutine` and swing, resets the combo, skips the recovery and clears the attack triggers. The Animator's Any State → Roll transition interrupts the attack animation, and the attack's stamina stays spent. Without stamina the roll is buffered until the attack ends, as before.

### Final boss (`Scripts/Boss/`, at the end of the Dungeon)

- `BossController` on the Dungeon's "Boss" object runs a two-phase fight. Each phase has its own health (`phaseOneHealth` and `phaseTwoHealth`, 250 each; damage beyond a phase's health doesn't carry over) and its own bar. Below `enrageAt` (0.5 of Astraía's health) she pauses less and adds rings/waves/stars. The fight starts when the player comes within `aggroRadius` or hits it. Each phase's bar comes from `StatBarUI.CreateBossBar`: it appears empty and fills up (`riseSpeed` with an invisible rise segment). The skeleton's bar is destroyed when it collapses, and Astraía's appears when she lands. It is a wide bar at the top center (the player's bars are bottom-left) with the phase name, in `BossController.nameFont` (Cormorant Garamond SemiBold, `Assets/fonts/SemiBold.asset`; Beckett was unreadable) uppercase with a black outline. The victory banner uses the same font on a dark band. Dying in the fight works like anywhere else: the defeat screen, then Try Again back to the last bonfire (there is one right outside the room). `BossController` no longer calls `BossRespawnPoint.Arm`, so the "BossRespawn" point is unused. Victory loads `MainVictory`.
- Phase 1 is `Models/Final_Boss/Phase_1/source/skeleton.fbx`, a 2.25 m skeleton scaled ×2.4. It is a Maya rig with namespaces: body bones `skeleton:*`, 10 floating hands with root bones `handN:arm_root`, and the halo `halo_outer_ring`. Its 14.6 s take "anim" loops through `Prefabs/Boss/Esqueleto_Fase1.controller`, and its `bg_plane` backdrop is hidden. Phase 2 is `Prefabs/Boss/Astraia_Fase2.prefab` (built by `BossAstraiaSetup`), a child of Boss that stays inactive until the transition and then hovers with a bob plus `HoverOffset`.
- Where each phase stands in Belén's room:
  - The Boss object, with the skeleton, stands in the middle of the room.
  - Astraía, still a child of Boss, keeps her own spot on the platform above the stairs. `phaseTwoBase` comes from her model's position, and `PhaseTwoGround` raycasts onto the platform.
  - `BossFightSetup.Build` keeps an existing Astraía where she is, and measures `phaseTwoCenterHeight` from her own root.
- `Scripts/Editor/BossRoomLayout.cs` applies the room changes by itself, once. It is versioned with `BossController.RoomVersion` and the hidden `roomVersion`, which `ApplyCodeDefaults` preserves. Version 1:
  - moves Boss halfway between Astraía and the `BossDoor`;
  - puts BossRespawn between the boss and the door;
  - sets `phaseTwoYawOffset` from her eyes `EYE L001`/`EYE R001` (front = Cross(right, up)), because the model doesn't face +Z;
  - boosts the room's window spot lights: the side windows from 600 to 2100 (range 45, 62°), the big window from 1500 to 4500 (range 50);
  - adds a `WindowLightShaft` to each window light.
  
  Version 2 brightens only the six side windows (`left windows`/`rigth windows`, sic) to 4500, with range 55 and 75°/45°. Pablo wanted them brighter and liked the big window (the downward light from above) as it was.
- `WindowLightShaft` (`Scripts/Ambiente`) fakes a volumetric beam, since URP has none: three crossed additive URP Unlit quads in the light's color, built at runtime and in edit mode on a HideAndDontSave object. They fade toward the edges and toward the floor, which a raycast finds.
- There is no hand-made animation: each model loops its FBX take, and attacks move parts on top of it in `LateUpdate` (the hands, the halo's emission through a MaterialPropertyBlock, Astraía's height). Attacks are `BossAttack` components on Boss, each with its phase, weight and cooldown:
  - `BossArmSlam`: a hand hovers over a red telegraph and slams; blockable. The number of slams in a row depends on `BossController.HealthFraction`: 1–2 above `midHealthBelow` (0.66), 1–3 below it, and 2–4 below `lowHealthBelow` (0.33), the only way to get 4.
  - Every floor telegraph (`BossTelegraph`) glows so it reads at grazing camera angles. The ring is HDR (×2.5, bloom) and slightly thicker (inner radius 0.86). Each telegraph also has its own point light of its color at half the radius above the center, intensity radius² + 2, that lights the whole zone's floor.
  - `BossHaloBolts`: a `BossChargeOrb` grows over the halo for `chargeTime` (1.3 s) while the halo glows red, then it fires bolts; blockable. Each bolt flies straight at where the player was when it was fired (`homing` 0, `spread` 6°). The orb is a glowing sphere with a strong point light. It starts at 40 % size so it reads at once, and pulses faster until the shot. The orb lights use intensity 450–600 and range 40–45: URP point lights fall off with the inverse square of distance, and at 20 the room tint was invisible beyond a few meters. That falloff still left the player and floor nearly untinted, so each orb also adds a directional light of the same color (`roomTint` 0.7–1.2, no shadows) that tints the whole room evenly while it charges.
  - Each of Astraía's attacks has a `warningColor`. Its `BossChargeOrb` above her eyes (`BossController.PhaseTwoHead`, from her `EYE*` renderers) and its floor telegraphs (`BossTelegraph.Spawn`'s optional color) use that color, so the color tells which attack is coming:
    - `BossProjectileRings`, blue: a 3 m circle under her, then expanding rings with a gap.
    - `BossShockwave`, red: the whole blast zone fills on the floor like the slam's circle (`chargeTime` 1.6 s, enough to run out of the 8 m radius) while she drops and shakes, then she blasts. The blast fills the zone: a big Vefects fire in the center (`SpawnImpactEffect` scale = radius / 2.5; Vefects child systems scale with the transform), `blastFires` (8) smaller fires toward the edge, the expanding ring and a strong flash at floor height.
    - `BossStarRain`, yellow: she rises and glows for 0.8 s, then yellow circles appear around the player where stars fall.
  - `groundY` comes from a downward raycast in Awake and `PhaseTwoGround` raycasts too, so floor telegraphs don't hide under the floor when the Boss object sits below it. The Boss object was moved after setup, and the shockwave zone had become invisible.
- Damage to the player goes through `BossFx.HitPlayer`, which uses `PlayerCombat.TryDefend` when the attack is blockable; `PlayerStats` ignores damage during roll i-frames. The player hits the boss through `BossHurtbox` (IDamageable) on "Hurtbox". Its solid capsules (one per phase) follow the active body, because PlayerCombat's sweep ignores triggers. In Awake, `BossController` adds `phaseOneHitboxPadding` (1.2 m) and `phaseTwoHitboxPadding` (1.8 m) to the measured radii (about 1.7 m and 1.5 m), at runtime only, so the scene keeps the measured size; the boss was hard to hit. The Editor.log showed the misses were fast swings that never reached the capsule, not the `minBladeSpeed` gate (5 in the Dungeon's PlayerKnight override). Astraía's capsule, `Center` and floor telegraphs follow her vertical axis through her eyes (`PhaseTwoAxis`), not the prefab root: `BossAstraiaSetup` centered the model on the bounds of everything, arms and spheres included.
- Everything an attack spawns is registered with `BossController.Track` and cleared on the phase change or death.
- Phase transition: the skeleton shakes, its Animator is disabled and code moves the hands and pelvis (collapse), then Astraía descends.
- Pacing: attacks are short (about 1–2.5 s) and separated by `pauseBetweenAttacks` (6–8 s, ×`enragedPauseMultiplier` 0.7 when enraged), so the player has windows to hit back. The pause only starts once nothing from the previous attack is still active (`HazardsActive`: projectiles, falling stars, telegraphs), waiting up to `maxHazardWait` (4 s). Pablo found 1.5–2.5 s and then 3.5–5 s pauses still too hard: the boss attacked about five times per player attack. The exception is the slam: Pablo wants it slow to land, so `windUp` is 1.6 s and its circle follows the player only during `trackTime` (0.5 s) before locking.
- `Scripts/Editor/BossFightSetup.cs` (Tools > Jefe > Armar pelea del jefe) builds all of this in the open scene and can be re-run. It also creates the effect materials in `Prefabs/Boss/Materials` (URP Unlit; HDR colors glow with the profiles' bloom). Re-running keeps the numbers of existing components.
- Code defaults do not reach a scene that already has the components by themselves, so the values are versioned. **When you change any default of `BossController` or an attack, bump `BossController.TuningVersion`.**
  - `BossFightSetup` is `[InitializeOnLoad]`. After every compile, on scene open, on `ExitingEditMode` and on `EnteredEditMode`, it finds bosses whose serialized `tuningVersion` is older. It applies the code defaults (keeping object references and `phaseTwoCenterHeight`/yaw offsets), sets the font, fits `aggroRadius` to the respawn point, marks the scene dirty and logs it. The user then only has to save.
  - If the compile happened when Play was pressed, it applies them to the play-mode boss only (no `MarkSceneDirty`, which throws in Play) and calls `BossController.OnTuningApplied`. The edit scene gets them on `EnteredEditMode`.
  - It never runs while exiting Play: `isPlaying` is true and `isPlayingOrWillChangePlaymode` false there.
  - The defaults come from a component added to an inactive temp object, so its Awake doesn't run.
  - Tools > Jefe > Restablecer valores del jefe does the same on demand.
  - The user never ran the manual reset, so a whole round of tuning silently didn't apply. That is why the automatic update exists.
- Lock-on finds nothing, the boss included: `PlayerController.enemyLayer` is Nothing in `PlayerKnight.prefab`.

### Cross-cutting patterns

- **Interfaces** (`Scripts/Interfaces/`): `IDamageable.TakeDamage(float)` is how everything deals damage (player weapon → enemies, enemy hitbox → player). `IInteractable.Interact(GameObject interactor)` is triggered by `PlayerInteraction`, which raycasts forward from the player on `interactableLayer` and resolves the component with `GetComponentInParent`. Implementers: `Door`, `LootItem`, `ShopTrigger`, `LootableItem`.
- **Hitboxes**: `WeaponHitbox` is a trigger collider disabled by default, toggled on only during the attack window by the combat script, and it raises an `OnHit` event instead of applying damage itself. `EnemyHitbox` is the enemy counterpart (activated during `EnemyDasher`'s dash). `EnemyDasher` also has a cyclic area attack (`secondAttack*` fields, started in `OnEnable`): about every 20 s, once the player is within `detectionRange` and no dash is running, it shakes `visualTransform` for 1.5 s and then deals 30 damage within 5 m through `Physics.OverlapSphere`, filtered by the "Player" tag.
  - Timings are random per attack, so several enemies don't attack in sync:
    - The tracking before each dash is `trackDuration` ±`trackVariation` (40 %).
    - The pause after a dash adds 0–`cooldownVariation` (1.5 s) to `attackCooldown`.
    - The area attack's first wait is 35–100 % of `secondAttackCooldown`, and later ones ±`secondAttackVariation` (25 %). When it was ready and waiting for the player, it fires 0–`secondAttackReactionMax` (2 s) after the player comes in range.
  - Gianluca's branch (`origin/Gianluca`, commit 1f80fe6 "scriptsEnemy") has `BaseEnemy`, a rewrite of an older `EnemyDasher` with a chaser behavior, a view cone with memory, and random pauses, plus a separate `Boss/BossEnemy.cs`.
    - Its `Enemy 1.prefab` swaps `EnemyDasher` for `BaseEnemy`, which would drop the animations, the animated death and the line-of-sight fix.
    - It was not merged. Only the random timings were carried over to `EnemyDasher`; porting the chaser would also need its animations.
- **Enemy model** (`Assets/Prefabs/Enemy 1.prefab`, 5 instances in the Dungeon that only override name and transform; it used to be a cube with sphere eyes):
  - The model is the "Masked Character" by Regulator (Sketchfab Free Standard, no credit required), in `Models/masked-character`.
  - It came without a skeleton, and Mixamo rejected the original FBX ("unable to map your existing skeleton") because of its ×4.44 node scale and offset. It was converted to a clean OBJ, auto-rigged in Mixamo, and saved as `MaskedCharacter.fbx`.
  - `Scripts/Editor/EnemyModelSetup.cs` builds the enemy. It is `[InitializeOnLoad]`, with `BuildVersionLabel` on the prefab and also Tools > Enemigos > Armar enemigo enmascarado.
    - It runs after a compile and on `EnteredEditMode`.
    - It never runs in Play. Builds 3 and 4 compiled when Play was pressed, never got built, and the new `EnemyDasher` asked the old controller for states it didn't have (`Animator.GotoState: State could not be found`).
    
    It does the following:
    - imports the FBX as Humanoid;
    - creates a URP material, with a mask made from the metallic, AO and roughness textures;
    - creates `Animations/Enemies/MaskedEnemy.controller`, with UAL2 clips plus Mixamo's `Sword And Shield Death`;
    - turns the cube (`visualTransform`, which still shakes) into "Modelo", holding the 1.9 m character. Its feet are at y = -0.5, where the cube's bottom was, and it faces +Z, the dash direction, measured from the legs;
    - shakes 80 % less than the cube did, since on the character the shake is only a hint: `shakeIntensity` 0.03 m in the dash's wind-up and `secondAttackShakeIntensity` 0.02 m at the end of the area attack's charge. Build6 lowers these once, and only if the prefab still has the cube's 0.15 and 0.1, so values tuned by hand are kept;
    - resizes the body BoxCollider to the character and hides the dash hitbox's red cube.
  - The Animator states are entered with `CrossFade`; the one-shots return to "Quieto" by themselves. `SetState` only cross-fades when the state changes:

    | State | Clip | When |
    |---|---|---|
    | Quieto | UAL2 `Zombie_Idle_Loop` | idle, or tracking when already facing the player |
    | Girar | DoubleL `1Hand_Up_Walk_A_F_InPlace` | turning toward the player, more than `turnAnimationAngle` (8°) away |
    | Carga | DoubleL `1Hand_Up_Crouch_Idle_1` | the 0.8 s shake before the dash |
    | Embestida | DoubleL `1Hand_Up_Sprint_A_F_InPlace` ×1.4 | the dash |
    | Zarpazo | UAL2 `Zombie_Scratch` | the area attack |
    | Golpe | UAL2 `Hit_Knockback` | when hit, only if not attacking |
    | Muerte | Mixamo `Sword And Shield Death` | on death |

    The enemy uses `DoubleL/FBX Unity` (humanoid, and `Combat1` uses its `Enemy_Attack_1`), so only `DoubleL/Demo` is unused.
  - Line of sight (`HasLineOfSight`): a ray from `eyeHeight` (1.25 m above the root) to the player's chest that skips the enemy's own colliders. It used to start 0.6 m in front at waist height and hit the enemy's own body when the player was beside or behind it.
  - Mixamo returned the FBX at 1.7 cm (it read the OBJ's meters as centimeters), so `EnemyModelSetup` raises the importer's `globalScale` (×110).
    - Build1 switched the FBX to Humanoid before rescaling it. The stored Avatar skeleton kept the old size ("Avatar Rig Configuration mis-match"), and in Play the skinned mesh collapsed: the enemies turned invisible.
    - Build2 compares the stored hips position with the model's. If they differ, it clears `humanDescription.human`/`skeleton`, and `autoGenerateAvatarMappingIfUnspecified` regenerates them.
    - The character's SkinnedMeshRenderer has `updateWhenOffscreen` on.
  - The Mixamo rig is correct. The OBJ faces +Z (the mask and the toes point that way) and `mixamorig:LeftUpLeg` is the real left leg (-X). Build4 swapped every Left/Right human bone because it wrongly assumed the rig was back to front. That didn't change which way the enemy faced; it only bent its arms and legs the wrong way. The back turned to the player came from the UAL2 clips (see below). Build5 swaps the bones back (`SidesSwapped`). The character keeps identity rotation and faces +Z, in edit mode too.
  - Clips keep their source file's facing ("Based Upon: Original"), and not every pack faces the same way. On each build, `FixFacing` plays every state on the avatar in a preview scene (`Animator.Play` + `Update(0)` at `FacingSampleTime`) and measures the body's front from the hips and shoulders.
    - If a state's clip leaves the enemy facing away, the state uses an enemy-only copy in `Animations/Enemies/Giradas` with Root Transform Rotation Offset +180°.
    - On this model the UAL2 clips face away: Quieto, Zarpazo and Golpe use turned copies. The DoubleL clips (Girar, Carga, Embestida) and the Mixamo death face forward. After Build5 every state measures +0.91 to +0.99.
    - The copies are rebuilt every time, and the original clips are never changed (the knight also uses the UAL2 ones).
    - Each copy gets its offset before `CreateAsset`, then it is force-reimported and measured as loaded from disk. At the end the build checks the offset in the saved file. In Build6 the offset was set after creating each copy, and creating the next copy reloaded the previous one from disk without it. The check passed in memory, but Quieto and Zarpazo were saved at 0, so after reopening Unity the enemy turned its back again.
    - The log lists each state's facing: +1 = toward the dash, -1 = back turned.
  - On death, if the enemy has an Animator:
    - it stops all coroutines and restores its colors;
    - it turns off its colliders and makes the Rigidbody kinematic;
    - it plays "Muerte" and is destroyed after `corpseDuration` (4.5 s). Without an Animator it disappears at once, as before.
- **Audio**: Unity audio and FMOD coexist. Unity audio stays enabled (`ProjectSettings/AudioManager.asset` `m_DisableAudio: 0`; Ariel's FMOD setup had turned it off): `PlayerFootsteps` (`AudioSource.PlayClipAtPoint`) and the Vefects fire prefabs' AudioSources use it. FMOD for Unity lives in `Assets/Plugins/FMOD` (~300 MB, its own `FMODUnity`/`FMODUnityEditor` asmdefs). Town's ambience is FMOD: `StudioEventEmitter`s on `Burning_House_SFX`, `Burning_Windmill_SFX`, `Well_Drip_SFX`, `Wind_Bells_SFX`, `Windmill_SFX` and the `Forest_Area`/`Town_Area` trigger zones, loaded by `Fmodbankload` (`StudioBankLoader`). The knight's MainCamera has both an `AudioListener` and FMOD's `StudioListener`; `PlayerKnightSetup` adds both (FMOD's through reflection, so the tool compiles without FMOD). The FMOD Studio project is not in the repo: `Plugins/FMOD/Resources/FMODStudioSettings.asset` points to `../../Crown-of-Heresy/Crown-of-Heresy.fspro` and its `Build` folder on Ariel's machine, and elsewhere FMOD only warns that the folder doesn't exist. The built banks are in the repo since Ariel's "Fmod fix 2": `Assets/StreamingAssets/Desktop/Master.bank` and `Master.strings.bank`, with ImportType StreamingAssets, so the events play on every PC. Ariel rebuilds and commits them when he changes the FMOD project. The old `Assets/FMODBanks` stubs are gone. Don't commit FMOD's local rewrites on PCs without the project: an empty `MasterBanks` in `FMODStudioSettings.asset` (Gianluca's commit had one; it was left out) and line-ending-only changes to the plugin's `.meta` files.
- **Input**: two approaches coexist. `PlayerInputActions.cs` is the generated C# class from `Scripts/Player/PlayerInputActions.inputactions` (used by `Combat1`/`PlayerController` via `new PlayerInputActions()`) — regenerate it from the asset rather than hand-editing. Some scripts read keys directly with `Keyboard.current` (`ShopTrigger`, weapon number keys in `PlayerCombat` and `Combat1`). Other scripts (`PlayerInteraction`, `InventoryUI`) query the project-wide actions via `InputSystem.actions.FindAction("Interact"/"Inventory")`, which come from `Assets/InputSystem_Actions.inputactions`. `WeaponManager` still uses the legacy `Input` class.
- **Health and stamina bars**: `PlayerStats` builds two `StatBarUI` at runtime: health in place of its `healthText` (the Canvas text, which moves inside the bar) and stamina right above it, fed by `OnStaminaChanged`. Health is burgundy, and its number uses `PlayerStats.barFont` (`Assets/fonts/BECKETT.asset`). The bars are sprite-less Images sized through `anchorMax.x`; a drop leaves a "chip" segment that waits `chipDelay` and then drains. `useHealthBar` off goes back to plain text. Stamina is spent by attacks (`PlayerCombat`, scaled by the weapon), rolls (`rollStaminaCost` 16), sprinting (`SprintStaminaCostPerSecond` 5/s; at 12 there was no stamina left to dodge the boss) and blocked hits (`TryDefend`); it regenerates at 15/s after 1 s without spending. At 0 stamina, sprinting stops until stamina is back to `PlayerController.sprintRecoverStamina` (25). The stamina bar is blue.
- **Cross-scene state is static**: `InventoryUI.inventory` (List<LootData>) and `InventoryUI.money` hold the player's items/money; `ShopManager.staticShopStock` holds the shop stock. `Door` checks keys by matching `LootData.ItemName` against `InventoryUI.inventory`. Its `requiredKeyName` is "Ancient Seal Key" (code default and `Door.prefab`), the key the shop sells. The key opens the boss room's door (`BossDoor`, see the Dungeon notes above); the other locked door, "Door (1)" in the Dungeon, is inactive. There is no DontDestroyOnLoad; the save system (below) stores and restores all of this.
- **Save system** (`Scripts/Guardado/`, started by Gianluca): `SaveSystem` writes a single slot, `partida.json` in `Application.persistentDataPath`.
  - What it stores: the scene, the player's position and Y rotation, the bonfire it was saved at, money, inventory, equipped weapons (by name) plus the one in hand, and the shop stock (`hayStockTienda` false if the shop never opened).
  - Items are stored by `ItemName` (plus description and price). On load they are looked up in `Resources/ItemRegistry.asset`, which `Scripts/Editor/ItemRegistrySetup.cs` keeps listing every `LootData` asset (rebuilt on compile and whenever an `.asset` changes; warns about duplicate names). Items missing from it are recreated with `LootData.Create`.
  - Saving: entering a `Bonfire`'s trigger range calls `SaveSystem.GuardarPartida(player, Bonfire.Id)` and shows "GAME SAVED" (`SaveNotice`, in the shop's title font). Re-entering the bonfire of the last save (`SaveSystem.UltimaHoguera`, also read from the file) doesn't save again. The Dungeon has three `Bonfire.prefab` instances; one is right outside the boss room.
  - Loading: `SaveSystem.CargarPartida()` (Load Game in `MainMenu`, Try Again in `MainDefeat`) restores the static state first: inventory, money, stock, and `PlayerCombat.RestoreEquipment`, which also marks the starting weapons as given. Then it loads the scene, and a `sceneLoaded` hook moves the whole player prefab to the saved spot.
  - `PlayerSave` is optional now (an autosave on scene start).
  - `SaveSystem.NuevaPartida()` (New Game) deletes the save and resets inventory, money, stock and equipment (`PlayerCombat.ResetEquipment`).
- **Death**: after `deathReloadDelay`, `PlayerController` records the scene (`SaveSystem.RegistrarMuerte`) and loads `defeatSceneName` ("MainDefeat"; the old `deathSceneName` "Dungeon" is gone).
  - The defeat screen uses `VictoryMenu`, which unlocks the cursor. Its Try Again button calls `VictoryMenu.Reintentar`: it loads the save, or, without one, the scene where the player died from its start. `MainVictory` still uses `VolverAJugar`.
- **Menus** (Gianluca, `Scripts/Menus/`):
  - `MainMenu`: Load Game is disabled without a save, Escape closes the panels, and `menuBotones` hides while a panel is open.
  - `OptionsMenu`: volume on FMOD's `bus:/` and brightness through `BrilloGlobal`, both saved in PlayerPrefs (`opciones_volumen`, `opciones_brillo`). `BrilloGlobal.Aplicar` replaces a Volume's `ColorAdjustments.postExposure` with the slider value, overriding the profile's own (the Dungeon's -0.3).
  - His MainMenu scene with the new panels isn't in the repo yet.
- **Items** are `LootData` ScriptableObjects (created as assets, or at runtime via `LootData.Create`). Enemies drop a loot prefab containing `LootItem`, which adds its `LootData` to the interactor's `InventoryUI`.
- **Scene flow**: `SceneTeleportTown`/`SceneTeleportDungeon` triggers and `SceneLoader.LoadNextScene` load scenes by name; the knight's death loads `"MainDefeat"` (`PlayerController.defeatSceneName`), and the old player's `PlayerHealth.Die` reloads `"Dungeon"`. Renaming a scene breaks these string references.
- Many components rely on the `"Player"` tag and on layer masks assigned in the Inspector (`hittableLayers`, `interactableLayer`, `obstacleMask`). Most tuning values are `[SerializeField]`, so prefab/scene overrides may differ from code defaults.

### Editing Unity assets

Don't edit `.unity`, `.prefab` or `.asset` YAML by hand unless necessary; wiring is normally done in the Inspector. Always keep `.meta` files alongside moved/renamed assets (GUIDs are how scenes/prefabs reference scripts).
